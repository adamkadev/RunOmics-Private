# Project audit — 24 September 2026

Repository structure, code quality (SOLID / KISS / Clean Architecture), CI/CD
duration, dependencies and OWASP Top 10, with an action plan.

**Scope.** All four repositories: `RunOmics-Private` at `abb665c` (the code),
`RunOmics` (public), `RunOmics-data-adam` and `RunOmics-data-lamiaa` (datasets).
About 51 000 lines of non-test code (42 000 TypeScript in `src/`, 7 000 Python,
1 900 Node/TS scripts) and 27 000 lines of tests.

**Method.** Read-only review, plus measurements:
- 90 GitHub Actions runs, broken down by job and step.
- Every test suite and build run locally with timings.
- `npm audit`, `pip-audit`, `npm outdated`, `knip` (dead code) and `madge` (import cycles).
- A co-change analysis over the full history (1 233 non-merge commits).
- Five parallel reviews: backend architecture, frontend, security, the Python pipeline, and the status of the previous audit.

Nothing in this document is an unfiltered lead. Every finding was reproduced or
read at the cited line. The **Conf.** column says how:
- ✔ re-checked by hand for this document;
- ● verified by a reviewer, by script or by reading;
- ○ suspected, because it depends on console settings that could not be seen (Vercel, Firebase, GitHub settings).

The previous audit, [`code-audit.md`](code-audit.md), was re-checked item by
item; see [§7](#7-previous-audit--status).

## 1. The answers, on one page

| Question | Answer |
|---|---|
| **Should the Git be split into several repositories?** | **No for the code; yes for the data, which is already split, and correctly.** 71 % of commits that touch Python also touch TypeScript, the coaching CLI imports the app's core directly, and there is one maintainer. Splitting would turn most features into two coordinated PRs and a versioned contract, for no team boundary to align with. Instead, give the one repository explicit units: web app, coaching CLI, Garmin sync pipeline, ops tools, a shared core and **data contracts**. Enforce the boundaries with lint rules and CI first, and move files later only if that is not enough. [§2](#2-repository-structure--should-it-be-split) |
| **Is the code clean / SOLID / KISS / Clean Architecture?** | **Good bones, soft boundaries.** The domain is pure: no I/O, no clock, no env, and its tests need no mocks. The coaching slice is textbook ports-and-adapters. Files are small (only 11 non-test files exceed 400 lines) and the comments explain *why*. The weak points are concentrated in a few places: the AI engine lives inside a 465-line route handler; disk JSON is cast to domain types, never validated; use-case files double as a type library (hence the type-only cycles); `src/lib` spans every layer; and there is measurable duplication (`DAY_MS` declared 18 times, 18 hand-written chart tooltips, 4 Python retry helpers). [§3](#3-code-quality-and-architecture) |
| **Is CI/CD too slow?** | **No.** PR feedback takes about **2 min 20 s**: CI (2 min 03 s) and E2E (2 min 18 s) run in parallel. The unit-test step went from 4 min to 60 s on 23 Sep. About half of E2E is setup that can be cached. **The real CI/CD problems are elsewhere.** The scheduled workflows fire **3 to 7 hours late**, and two of them have **failed every day for at least 6–8 days** on the `lamiaa` deployment with nobody noticing. [§4](#4-cicd) |
| **Dependencies?** | **Healthy.** 0 known vulnerabilities in production npm dependencies, 0 in pip. 4 dev-only advisories, fixed by a vitest patch and an eslint update. 2 unused packages (`gpxpy`, `vitest-axe`). The one real gap is supply chain: the nightly sync installs **unpinned** Python packages in the same job that holds the Garmin token and the data-repository write token. [§5](#5-dependencies-and-supply-chain) |
| **OWASP?** | No injection, XSS, SSRF or broken-auth paths were found, and the auth code is careful. The top issue is **privacy**: the privacy zone only trims route ends at a fixed radius, so the public routes' endpoints form a ring whose centre, the protected location, can be computed from a handful of runs. **The five things to do first** (all small; details in [§8](#8-action-plan)):

1. Fix the privacy zone: a random extra trim per activity, a larger radius, and a verifier that actually asserts. Then re-crop the stored routes.
2. Find out why `lamiaa`'s deployment returns HTTP 500 on `daily-session` and `stale-sync-check` (Vercel logs; Firebase Admin credentials are the likely cause), and make the health endpoint report it.
3. Close the three confirmed data-loss paths in the Python sync (corrupt file skipped then overwritten; post-save failure discards the night; 5xx stored as "no data").
4. Install Python dependencies from a hash-locked file, give Vercel a read-only data token, and add rulesets that block force-push and deletion on the data repositories.
5. Move the cron times off the hour, and add `permissions`, `concurrency` and `timeout-minutes` to every workflow.

## 2. Repository structure — should it be split?

### 2.1 What exists today

| Repository | Visibility | Role | Activity |
|---|---|---|---|
| `RunOmics-Private` | private | the canonical code: web app, Python sync, coaching CLI, ops scripts, 9 workflows | 1 311 commits since 12 Jun, about 15 a day on active days |
| `RunOmics` | **public** | MIT portfolio snapshot: 8 commits, last code change 17 Aug | 224 private commits behind; 443 of the 591 shared files differ |
| `RunOmics-data-adam` | private | one athlete's dataset (47 JSON files, 15 MB) | nightly bot commits, plus manual coaching edits |
| `RunOmics-data-lamiaa` | private | the second athlete's dataset | nightly bot commits |

Inside `RunOmics-Private` there are already five runnable units, with no enforced
boundaries between them:

| Unit | Language | Non-test lines | Runs on | Talks to the others through |
|---|---|---:|---|---|
| Web app (`src/app`, `src/components`, `src/i18n`) | TS / React | 23 500 | Vercel × 2 | imports core |
| Core (`src/domain`, `application`, `infrastructure`, `lib`) | TS | 18 800 | inside web and CLI | — |
| Coaching CLI (`scripts/coaching*.ts`) | TS | 430 | laptop | 10+ dynamic imports of core (`scripts/coaching.ts:121-126`) and a spawned Python bridge (`PythonGarminGateway.ts:37,47`) |
| Garmin sync pipeline (`scripts/**/*.py`) | Python | 7 000 | Actions, nightly | writes about 25 JSON files that 19 TS repositories read |
| Ops tools (`scripts/*.mjs`) | Node | 1 460 | Actions and Vercel build | clones and pushes the data repository |

### 2.2 The evidence

**Co-change** over the full history of `main` (1 233 non-merge commits):

| Commits touching… | Count | …that also touch TypeScript |
|---|---:|---:|
| Python (`scripts/**/*.py`) | 87 | **62 (71 %)** |
| Coaching core (`src/*/coaching`) | 36 | 23 also touch the rest of core; 14 also touch the CLI |
| Web UI | 1 021 | 361 also touch core |

The Python/TS commits are vertical features, not incidental edits:
- "sync training status from Garmin and surface it" (`1f2fc52c`);
- "store Garmin training-status history and load balance" (`b03a0808`);
- "sync SHOE_REGISTRY from Garmin's gear-service" (`40f1b402`).

Each one changes the producer (Python), the implicit contract (JSON shape) and the consumer (a TS repository and the UI) at once.

**The contract is implicit.**
- There is no JSON Schema, and the shapes are written three times by hand: Python `to_dict` (`mapper.py:71-109`), the TS domain types, and the demo generator (`generate_demo_data.mjs:675-691`).
- 16 of 19 TS repositories cast what they read (`readJsonFile.ts:37` ends with `parsed as T`).
- The bridge protocol is ordered JSON lines with no request id or version (`sync_bridge.py:10-25`, `PythonGarminGateway.ts:82-101`).

### 2.3 Options

| Option | What it is | For | Against | Verdict |
|---|---|---|---|---|
| **A. Status quo** | one repo, boundaries by convention | free | the boundaries drift (§3.2); Python has no packaging, lint or type check; every change runs every check | not enough |
| **B. Polyrepo** | `runomics-web`, `runomics-sync` (Python), `runomics-coach`, and `runomics-core` as a published package | boundaries by construction; independent CI | 62 of 87 past Python changes would each have needed two coordinated PRs and a contract version bump. `core` would have to be versioned, published and bumped in two consumers. Secrets and environments would be duplicated. Checking that the app reads what the pipeline writes gets *harder*. One maintainer means no team boundary to mirror (Conway). | **not valuable** |
| **C. Modular monorepo** ✅ | one repo with explicit units: several projects in one solution | enforced boundaries; explicit contracts; per-unit CI filters; Python gets real tooling | a few days of mechanical moves if done physically | **recommended, in two steps** |

### 2.4 Recommendation

**Step 1 — no file moves (Phase 1 of the plan).** This gives most of the value:

1. **Contracts first.**
   - Add a JSON Schema for each data file the app cannot live without (activity month files and `index.json`, `athlete.json`, `goals.json`, `pbs.json`, `planned_workouts/*`, `shoes.json`, `upcoming_races.json`).
   - Validate against them in three places: in Python before the push, in the TS repositories on read, and in a small workflow in each data repository.
   - An unknown activity type should map to `other`, not crash five pages.
2. **Enforce the layer rules** with `@typescript-eslint/no-restricted-imports` (already installed through `eslint-config-next`). Every cross-layer import uses the `@/` alias, so the zones are easy to write.
   - Start at `warn`, with today's 17 page/route→repository bypasses allowlisted.
   - Add `madge --circular` and `knip` to CI, so that *new* cycles or dead files fail the build.
3. **Give the Python pipeline its own `pyproject.toml`** (ruff, mypy basic, pytest config) and a hash-locked requirements file.
4. **Path filters in CI:** a Python-only change skips E2E, and a docs-only change skips everything.

**Step 2 — physical layout, only if Step 1's allowlist stops shrinking** or the
pipeline or core gains a second consumer:

```
apps/web/          ← src/app, src/components, src/i18n, public/, next.config.ts   (Vercel root)
apps/coach/        ← scripts/coaching*.ts, coachingRules.ts
packages/core/     ← src/domain + src/application (no next, react, firebase, fs)
packages/adapters/ ← src/infrastructure + the server-side parts of src/lib
pipeline/          ← Python: pyproject.toml, src/runomics_sync/{garmin,processing,repository}, tests/
contracts/         ← JSON Schemas for data/*.json and the bridge protocol, plus golden fixtures shared by pytest and vitest
tools/             ← fetch/push/prepare data, verify_no_private_data, demo generator
```

Use plain npm workspaces; no Turborepo or Nx is needed at this size. As an ESM
workspace package, `core` also removes the Node 22 CJS interop shim
(`scripts/interopImport.ts`) that exists only because of how tsx compiles the
CLI today.

### 2.5 What should move *between* repositories

| Item | Where it is | Where it belongs | Why |
|---|---|---|---|
| `make-plan.mjs` (root) | code repo | data repository, or delete | A one-off that hard-codes one athlete's paces and dates and writes `answer.json`, which `.gitignore:20` ignores because "it carries health data". knip lists it as unused. ✔ |
| `.claude/skills/coaching-plan/references/methodology.md:154-158` | code repo | data repository (or a git-ignored local file) | holds the athlete's LTHR, HR-zone floors and injury review ● |
| `public/events/*.jpg` (race photos) | code repo (none tracked today) | each data repository | already listed as "known sharing" in `personal-deployments.md` |
| The athlete list (`adam`, `lamiaa`) | hard-coded 5 times in workflows (`sync.yml:23,40`, `internal-notify.yml:27`, `capability-audit.yml:9,27`) and in `compare_reports.py:23-29` | **one** repository variable, `vars.PROFILES`, read with `fromJSON` | adding an athlete should not need code changes (open/closed) ✔ |
| `RunOmics` (public) | frozen snapshot | either archive it (banner plus GitHub "Archive"), or export automatically on release tags through an allowlist and `verify_no_private_data` | it silently diverges; it is clean today (secret scan of all 8 commits: nothing; the verifier passes; schedules disabled) ✔ |

**Keep the data repositories separate.** Personal health and GPS data needs its
own access control, lifecycle and retention. That split is right. It needs
protection (§6, A08) and a contract (above), not a merge.

### 2.6 When to revisit

Split out a repository only when one of these becomes true:
- a second person owns the pipeline;
- the pipeline or core is reused by another product;
- release cadences diverge (for example, the app is released publicly while the pipeline stays private);
- the Step 1 lint allowlist keeps growing.

## 3. Code quality and architecture

### 3.1 Strengths — keep these

- **Pure domain.** `src/domain` has 0 imports from infrastructure and never calls `new Date()`, `Date.now()` or `process.env`. Its 47 test files need no module mocks. ●
- **The coaching slice is the template to copy.**
  - 4 ports and real composition roots (`scripts/coaching.ts:120-130`).
  - `now`, `id`, `pause` and `persist` are passed in (`workflows.ts:38-43`).
  - A checkpoint after each Garmin mutation (`garminSyncApply.ts:121-131`).
  - Plans are validated on read and write (`JsonCoachingRepository.ts:52-73`).
  - 11 test files and 0 `vi.mock`. ●
- **Thin, uniform HTTP edge.** `handleInternalRoute` and `handleOwnerRoute` wrap every guarded route, and 14 of the 16 routes are 35 lines or fewer. ●
- **Little ceremony.** 3 of the 4 ports earn their keep, and no interface has only one implementation except `WorkoutPublisher` (§3.3). ●
- **Bundle hygiene.** None of the 115 `'use client'` files reaches crypto, fs, firebase-admin or exceljs at runtime. ●
- **Python history files** fail closed on corruption and write with tmp+rename (`history_file.py:20-63`). 323 of 326 functions are type-annotated. ●
- **Test volume.** 1 951 vitest tests, 364 pytest tests and 11 E2E tests pass locally in 33 s, 8 s and 7 s. Lint and typecheck are clean. ✔

### 3.2 Layering

**Import matrix** (value/type imports, non-test; `.` means none):

```
from \ to   domain  usecases  coaching  ports  infra   lib   i18n  UI-pkg
domain        -       0/9        .        .      .     12/0   2/0   1/1

```

Reading it:

- **Domain → application (9, all type-only)** and **infrastructure → use cases (3)** exist because use-case files double as the type library. `AthleteProfile` is even defined in a repository (`JsonAthleteRepository.ts:23`). This causes all 5 application-side cycles madge reports, for example `GetGoalsData ↔ JsonGoal/JsonPb/JsonUpcomingRaceRepository`. They are type-only, erased at compile time, but they tangle the layers. ✔ (madge: 7 cycles in total; also `i18n/index ↔ fr`, type-only; `SeasonTimeline ↔ YearView`, runtime; and `GlobalMapWrapper ↔ GlobalMapClient`, a `next/dynamic` import, harmless.)
- **The domain imports `lucide-react`** (`domain/activity/types.ts:1-3,190-208`), and the list of valid activity types is *derived from the colour map* (`api/activities/route.ts:6`). ●
- **50 of 54 use cases import concrete repositories.** That is a pragmatic layered style, not strict Clean Architecture, and **that is fine here**: each JSON file has a single implementation, and adding a port per file would be ceremony. Keep ports where they pay:
  - where there are two or more implementations (the Gemini and manual coaching advisors);
  - for an external system you must fake (Garmin, Gemini, Firestore). ●
- **`src/lib` spans every layer:** about 25 pure utilities, 9 SDK/IO adapters (`gemini`, `firebase-admin`, `sendPushNotification`…), 12 hooks, 6 canvas modules and 2 application services (`aiSpend`, `verdictStatus`). So "domain may import lib" cannot be written as a rule. ●
- **17 page/route → repository imports bypass the use cases** (14 in pages; `ai-insights/route.ts:85-92`, `health/route.ts:3`, `location-override/route.ts:2`). ●
